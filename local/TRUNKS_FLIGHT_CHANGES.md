当前运行差异为两个文件：

- `src/battle/btl_act_d.c`：ENTER 仍仅识别角色 41、命中动作 0x12E、技能 slot 3/ID 0x163；work[19]=5 表示 4 次等待决策加结束标记。原方向 bit 1 不再屏蔽，只去除飞行键触发普通飞行和侧跳的 mask `0x1E018`。neutral、free move、close move 共用同一个小函数；四次决策之后恢复普通飞行的距离检查。close move 在此上下文中可直接检查普通飞行，避免多走一次 free move 转换而额外多等一帧。所有原方向运动 RUN、攻击、防御、蓄气、升降、必杀技判定及调用顺序保留。
- `src/battle/btl_char_action.c`：原 scratch 清零会在方向移动切换动作时丢失计数。仅在 B/D/E（neutral/free move/close move）相互转换时保留 work[19]；其它状态仍按原逻辑清零。其它 scratch、动作帧、调度顺序、输入和回滚都不改。这样方向立即走原移动动作，飞行计数也不会因动作切换重启。

没有静态状态、墙钟或原始本地手柄依赖。角色 scratch 已在原快照范围中。没有改联机、协议、回滚或输入文件。

210 项检查通过：真实 neutral/free move/close move 和原主决策/输入查询，加入真实 dispatcher 的 LEAVE→scratch 清零→ENTER→RUN 流程；八方向+飞行第一帧全部进入原移动且请求非零运动速度，四次等待后进入飞行；跨近身/普通移动不重置计数；攻击、防御、蓄气、升降/高速升降、龙冲在三个移动状态中均与原 mask 同帧响应；松键方向持续、原飞行松键判定、其它角色和快照重执行检查通过。完整飞行动作源码仍与 r20 相同。

检查的运动服务是桩，验证的是原运动函数收到速度请求，不能冒充实机位移/碰撞或公网验证。当前入口 `TrunksFlight-Test4.exe`，等待用户比较方向和 4 帧手感；Test3 保留可随时对照。源码端点、增量/完整补丁及回放验证保存在 `flight-only4-20261103/records`。以下为 Test1..3 的历史分析与实现记录。

## Test3 历史代码调整（当前实现见顶部 Test4）

唯一运行源码变化：`src/battle/btl_act_d.c` 的 `BtlAct_NeutralHandler`。

1. 仅在 neutral 的 ENTER 中检查 `prev == 0x12E && chara == 41 && BtlSuper_GetId(chr,3) == 0x163`，成立时在原有 `work[19]` 留下标记 1。
2. DECIDE 中只在 `work[19] && actionFrame <= 5 && DASH held` 时，暂时从本次原 movement mask 去除普通飞行、侧跳/前冲和方向移动组。第 6 个决策帧恢复原 mask。
3. 沿用原 dispatcher 维护的 `actionFrame`，不添加倒计时、不清除或伪造输入。飞行动作中的松键、惯性、方向和停止判定完全沿用原版。防御、攻击、蓄气龙冲、强制受击仍走原流程。
4. 仅复用一个原有 per-action scratch 作标记；原 dispatcher 在动作切换时清零，回滚的原 heap 快照已覆盖它。没有全局静态状态、墙钟或本地手柄依赖。ENTER 后 RUN/UpdateTimers 将动作帧从 0 加到 1；随后 DECIDE 的帧数依次为 1..5。
5. 改动包在 `#ifdef PORT` 内；PS2 匹配构建沿用原代码。

没有改动联机、协议、输入记录、回滚、渲染和资源文件。只有 `battle_btl_act_d.o` 发生变化，其余代码对象及全部数据对象与 r20 逐字节一致。
战斗行为已变化，测试联机时双方应使用相同构建，不能据协议号相同就视为与旧程序兼容。

## 验证与边界

`local/tests/run_trunks_flight.py` 编译从生产源码直接提取的 neutral、原 `BtlDecide_Main` 及完整相关输入查询，模型/场景服务替换为测试桩。
51 项检查通过：实际采样输入、5 帧窗口、普通/其它角色/其它形态/技能/未命中情形、松开不重置原动作帧、原飞行松键宽限及方向持续、防御/攻击/蓄气龙冲/强制受击和角色快照重执行。测试现在模拟真实 `BtlChar_BeginFrame` 对 prev 的刷新。测试脚本还逐字比较了完整 `BtlAct_DashMoveHandler`，确认与 r20 一致。
构建使用原 Windows 指针转换与软件浮点流程，链接成功，原有 103 个未实现桩数量保持不变。

第一轮 `TrunksFlight-Test.exe` 的只读实测中，两次完整长按序列都是 `0x12E -> 0xB`，等待 5 个决策帧后直接进入飞行 `0xF`。用户确认“修改奏效”，并强调原版松开按键继续飞行的机制必须保留。

第二轮试图去掉标记，直接在后续 DECIDE 检查 prev。2026-11-03 用户实测该版重新出现侧跳。原因：`BtlChar_BeginFrame` 每帧执行 `chr->prevAction = chr->action`；neutral ENTER 时 prev 为 `0x12E`，但下一决策帧已是 `0xB`。2026-11-02 已保存的只读采样也显示这个变化。先前测试错误地让 prev 一直停留在技能 ID，未覆盖这个真实生命周期。

修正测试模型后，未修改的第二轮代码第一帧就失败（`followup-20261103/test2-regression-result.txt`）；第三轮用上述 ENTER 标记修复，并通过 51 项检查。飞行动作函数不变，无松开取消分支。第三轮入口 `TrunksFlight-Test3.exe`，第二轮端点和新增补丁分别保存在 followup 记录中。第三轮尚待用户实机验证。

逻辑桩测试不代替实际渲染、碰撞位移或公网联机验证。
